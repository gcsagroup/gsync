# 开发计划

文档版本：0.1  
更新日期：2026-11-06（北京时间）  
状态：保留原始阶段计划；已实施首轮开发候选，尚无完整阶段验收通过

本轮实际进展见[统一验收报告](12-unified-validation-report.md)。M0—M5 有部分实现／验证，M6 公开试用条件未满足；Windows／Android 等后续阶段尚未完成。下列通过标准保持不变，不能用自动化子项通过代替整阶段验收。

## 1. 执行原则

收藏夹和密码库一起完成最小流程，再扩充覆盖范围。不能先写完整界面，再发现外部来源没有可用接入路径。

实施按“步骤 → 证据 → 通过标准”推进。产品范围以[产品需求](01-product-requirements.md)为准，外部能力以[兼容性与可行性](02-compatibility-and-feasibility.md)及实测证据为准。不要把文档状态改成已实现来代替工程交付。

本文安排顺序和依赖，暂不承诺日历发布日期。准确系统版本、签名资源、开发人力和关键连接器结果尚未明确，M0 后再根据实际耗时安排工期。

## 2. 阶段边界

| 阶段 | 定义 | 可以得出的结论 |
| --- | --- | --- |
| 文档基线 | 本次交付 | 需求与计划已整理；不证明任何产品功能完成 |
| 内部原型 | 小样本、测试账号、受控环境 | 某一技术路径是否可用；不开放真实密码大范围试用 |
| 首轮公开试用 | Mac＋iPhone、自备存储、明确支持矩阵 | 已验收的组合可安装使用；没有公开官方云承诺 |
| 扩展平台 | Windows／Android／iPadOS | 每个平台独立测试、签名和能力声明 |
| 官方云运营 | 另行安排 | 在成本、运维和公开部署范围确认后上线 |

首轮公开试用保留完整保险库目标与 Mac App 填充目标。内部原型先只用简单账号，不代表将其他条目类型默认为以后再做。若某项已确认范围无法完成，记录阻塞并明确调整，不能悄悄缩小验收标准。

## 3. M0：可行性与工程基准

前置：已完成需求基线；不访问真实保险库作为默认测试样本。

| 任务 | 步骤 | 交付与验证 |
| --- | --- | --- |
| M0-01 设备基准 | 核对 Mac、iPhone 17 Pro Max 的系统版本、构建号、正式／测试分支和测试权限 | 设备清单；不能把“最新版”作为版本号 |
| M0-02 浏览器接入 | 在 Mac 的 Chrome、Firefox、Edge、Aegis 安装最小测试扩展，读写合成收藏夹 | 原生收藏夹截图／事件记录、配置文件隔离、卸载恢复验证 |
| M0-03 Aegis 核查 | 确认另一个项目位置和当前版本，只研究扩展可用性 | 扩展接入说明；发现确需源码修改时另列变更，不在本任务隐式改原生浏览器 |
| M0-04 Safari 文件 | 用含中文、嵌套目录、重复 URL 的测试文件在 Mac 与 iPhone 双向导入导出 | 目录、排序、重复项和删除行为差异报告；不再研究其作为首版自动同步硬门槛 |
| M0-05 iPhone 自备存储 | 从 iPhone 直接访问测试 WebDAV 与系统授权文件夹，Mac 关闭后重测 | 两种路径独立读写；目录失效、网络中断、文件未下载的结果 |
| M0-06 外部密码源 | 使用合成 1PUX、CSV、KDBX；测试 1Password 授权读写与 KeePass 往返 | 字段对照、未知字段、锁定、重授权和并发报告 |
| M0-07 填充与凭据交换 | 最小 Apple 提供器、网页扩展、Passkey 交换和 Mac 样本填充 | 对每种实际填充入口给出成功／受限结果，不把跳转网页计为桌面填充 |
| M0-08 格式与选型 | 评估共享核心、自有格式、KDBX 库、加密库、许可证与 App Store 集成 | 一份定稿选型记录、依赖清单、协议草案与测试计划 |

**通过标准：** 每个首轮核心路径都有复现步骤及结果；无路可走的功能记录明确限制或阻塞。不能仅凭 API 文档让 M0 通过。iPhone 自有库不依赖 Mac、两种自备存储和可信恢复设计是核心路径。

**失败处理：** 保存首次失败证据，定位修复后重测相关场景；无法完成的已确认需求单独报告，不用跳过测试、私有接口或降低系统保护绕过。

## 4. M1：数据核心、加密与本地恢复

依赖：M0 的格式、依赖、密钥与版本规则定稿。

任务：建立工程和最少模块；实现数据空间、条目模型、本地事务、密钥封装、恢复材料、历史与删除记录。为未知字段保留扩展区，给所有类型设置版本兼容策略。

交付：单机可创建、解锁、编辑和导出加密测试库；能在干净安装恢复；能够区分收藏夹和保险库解锁状态。

验证：跨语言／平台测试向量、错误口令、篡改、随机数和 nonce 使用、进程中断、附件完整性、旧格式升级与失败回滚。任何未经验证的密钥方案不得进入真实密码试用。

通过标准：T01、T05、T08、T16—T19、T22、T26、T39 的相关单机部分通过，仍不表示多设备或填充完成。

## 5. M2：Mac＋iPhone 双端最小流程

依赖：M1；M0 的 iPhone 存储原型通过。

任务：同时接入收藏夹与一组测试账号；实现 WebDAV、本地文件夹、离线队列、同步状态、幂等合并和“较新版本优先＋历史恢复”。建立不依赖官方账号的设备接入流程。

代表性操作：Mac 新增收藏夹和测试密码 → iPhone 收到 → iPhone 离线修改 → Mac 同时修改 → 重连合并 → 恢复旧版本 → 新设备恢复。WebDAV 和文件夹各跑一遍。

交付：两个可运行客户端与复现记录；官方账号服务关闭时仍可使用自备存储。

通过标准：T01—T09、T16—T19、T30、T37、T40 的相关双端部分通过。iOS 后台不承诺固定周期，前台补传必须可靠。

## 6. M3：浏览器与来源数据接入

依赖：M2；各连接器 M0 结果。

任务：完善 Chrome／Firefox／Edge／Aegis 收藏夹扩展、根映射、事件去重和首次合并；实现 Safari 手动文件交换；完成保险库按库映射、1PUX／CSV／KDBX 迁移报告。

持续连接先以测试库验证一个可写回的来源，再扩到其他来源。1Password 授权与 KDBX 文件写回采用各自适配，不硬塞入“所有来源都实时同步”的接口承诺。

交付：来源能力清单，包含读／写／迁移／填充、类型范围、版本和限制；接口可读不代表可以开始破坏性写回。

通过标准：T10—T14、T27、T28、T31、T36、T38 通过对应来源用例。完整类型的 T15 和保存／填充的 T20、T21 在 M4 验收，避免阶段依赖倒置。Safari 必须做目标应用实际导入，不能仅用本产品解析回读。

## 7. M4：完整保险库、保存与填充

依赖：M1 类型模型、M2 同步、M0 系统能力原型；可与 M3 中独立的解析工作交错执行。

任务：完成全部条目类型、附件、TOTP、Passkey 提供与迁移能力验证；完成网页、iPhone App、Mac 桌面样本的填充；分别实现保存和填充设置。

默认确认保存、主动触发填充；用户可按规则开启自动保存和指定网站自动填入。不自动提交登录。身份不明确、库锁定或保存检测不可靠时，不猜测条目或目标。

交付：类型保真表、目标网站／App 版本及实测矩阵、填充失败可理解提示。不得把手动复制密码计为自动填充通过。

通过标准：T15、T19—T26、T29、T34、T39、T42 通过。Passkey、Mac App 或关键字段未通过时保留阻塞，不用“完整保险库”文案掩盖限制。

## 8. M5：本地官方云与统一可靠性验证

依赖：M2；在对外试用前完成本地云核心验证。

任务：运行本地服务，验证官方账号与解密分离、密文存储、版本条件、备份恢复、无权限拒绝及设备撤销。官方云适配器共用客户端同步逻辑，不另造一套冲突规则。

本地开发服务若需容器，尽量复用一个容器、镜像和数据卷，按场景切换 WebDAV／云测试服务。不可为压力测试启动未获授权的付费资源或公开端口。

交付：本地云演示、部署草案、备份恢复演练和资源测量。不得把本地通过写成公开云已上线。

通过标准：T05、T08、T17、T18、T30、T32、T33、T37 通过相应后端；自备存储测试时关闭该服务，再确认无依赖。

## 9. M6：Mac＋iPhone 首轮公开试用准备

依赖：M3、M4、M5；所有适用发布阻塞用例通过。

任务：整合 UI、权限引导、无障碍操作、状态文案、错误恢复、文档、签名和分发；安装到真实 Mac 与 iPhone。按实际支持程度生成能力表，实验性连接默认关闭。

首轮公开试用仅开放 WebDAV／文件夹；不要求官方账号，不开放公开官方云。iPhone 最终必须可上 App Store；TestFlight 可作为试用分发步骤，但不能据此写成 App Store 已上架。

交付：可安装包、固定路径与版本记录、全套测试结果、恢复说明、已知限制、开源许可证和依赖清单。签名凭据、付费账号、硬件或测试账号缺失时记录待办，不伪造完成。

通过标准：所有适用 T 用例与发布检查完成；损坏数据、越权填充、秘密日志、错误覆盖、恢复失败为发布阻塞。仅功能编译成功不能通过 M6。

## 10. M7：后续平台与官方云运营

Windows 和 Android 是明确的交付平台。先用 Android 模拟器和 Windows 远程机验证两端客户端，沿用 iPhone 模拟器验收使用的数据格式与同步规则。iPhone 真机另行验收。

- **共用验收**：打开既有加密备份，复用版本合并、删除记录、附件和目录排序的样本与格式测试向量。先在各端实现收藏夹与密码库的查看、管理、恢复和同一 WebDAV 位置的双向读回，再逐来源接入。
- **Windows**：桌面客户端使用 C++ 和 Win32，构建为一个可直接启动的 EXE。来源接入优先验证 Chrome、Edge、Firefox 的书签扩展和 Windows 本机消息宿主。以独立浏览器配置验证运行中读写、排序、重启和删除。浏览器密码、KeePass 和 1Password 逐项验证读取、写回、并发冲突与权限恢复。[Microsoft Edge 本机消息](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/native-messaging)
- **Android**：先验证 App 内同步与系统后台补传，再验证 Credential Manager 和自动填充是否能使用 PBsync 自有凭据。Android 浏览器、KeePassDX 和 1Password 的来源接入按各应用公开支持的接口或文件交换实测，逐项记录数据方向和授权。[Android 凭据提供器](https://developer.android.com/identity/sign-in/credential-provider)

iPadOS 沿用 Apple 数据格式和验收用例，单独验证布局及系统接口。

官方云公开运营另设成本、容量、备份周期、告警、服务恢复和实际部署决策。免费不等于无限存储，附件和备份成本测量后确定额度；本次不设收费计划。

家庭／团队共享、付费功能、Aegis 原生内置同步均不在当前首版计划内。

## 11. 构建、版本和环境约定

- Mac App 构建、运行和测试尽量固定在同一路径。初次构建前记录路径，建议 `build/GCSA-PBsync.app`，确认后复用。
- 每次实际构建、编译或打包递增构建号。小修采用 `Ver 1.0 (xxx)`，新增功能用 `Ver 1.1`，多个功能或大范围改变用 `Ver 2.0`；这是用户约定，尚未生成首次应用版本。
- 构建记录包含源版本、构建号、路径、签名方式、测试设备和结果。版本号不能代替质量验收。
- 尽量一个项目一个开发容器、镜像和数据卷；无必要不使用 Docker。
- 不删除用户已有数据、其他项目构建物、worktree 或真实保险库作为测试清理步骤。
- Aegis 是另一个项目，首轮只以扩展接入；若必须改源码，明确列出独立变更范围。
